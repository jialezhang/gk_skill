用一段话回答：

1. 核心 Goal 是否达成；
2. 哪条精确用户旅程已实际执行；
3. 最强验收证据是什么；
4. 哪些内容仍未完成、未验证或不在范围。

然后用表格区分 `IMPLEMENTED / ENABLED / EXECUTED / VERIFIED`。

## 六、哪些做法有效

每项写成：

`行为 → 产生的结果 → 对应证据`

保留真实降低返工、发现产品缺陷、保护数据或增强可复现性的做法。

## 七、问题、根因与恢复

每项包含：

- 现象；
- 直接原因与系统性根因；
- 造成的成本、时延或风险；
- 本轮恢复动作；
- 防复发门禁。

不要把测试发现的真实缺陷写成“测试拖慢”，也不要把工具缺陷误报为产品架构限制。

## 八、下一轮执行清单

按阶段组织：

### 开始前

- 冻结目标身份、范围、矩阵分母和统计口径。
- 准备隔离环境、受保护资源、运行入口、外部副作用策略和最低成本 thin slice。

### 执行中

- 对关键运行记录 source identity 和有效性。
- 代码或目标改变后作废旧验收。
- 同因基础设施失败三次时停止矩阵并修根因。

### 验收时

- 在精确目标上运行核心旅程。
- 对账交互入口、API、受保护资源、外部副作用和 Git/build 身份。
- 候选冻结后再执行最终全量回归。

将项目特有规则补充为可检查条目，而不是泛泛建议。

## 九、计划与验收对账

| 计划项 / Gate / 用户旅程 | 状态 | 精确证据 | 备注 |
| --- | --- | --- | --- |
|  | `VERIFIED / BLOCKED / DEFERRED / INVALID` |  |  |

核心项存在 `BLOCKED`、未批准的 `DEFERRED` 或缺失证据时，不得写 Goal 完成。

## 十、剩余风险与非目标

区分：

1. 当前交付的已知风险；
2. 未执行的环境或矩阵；
3. 明确不在本 Goal 范围的能力；
4. 需要新 Goal 或外部授权的后续工作。

## 十一、权威证据索引

列出 Goal 回执、PRD、实施计划、delivery/acceptance、原始测试输出、Git identity、run/job/release ID。说明本复盘不替代原始证据。

## 推荐的精简版

用户只要求简短复盘时，保留：

1. 结论；
2. Goal 身份与统计；
3. 交付/验收对账；
4. 作废证据与主要偏差；
5. 下一轮三条行动；
6. 权威证据索引。
