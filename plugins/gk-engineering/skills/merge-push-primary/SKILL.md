# Merge Push Primary

Merge the current branch's committed and intended uncommitted changes into local `main` before committing and pushing. Finish checked out on `main`, then safely delete the original local branch. Preserve unrelated changes and remote source branches. An explicit user-specified target overrides `main`; never silently substitute the remote default branch.

## Workflow

1. Inspect `git rev-parse --show-toplevel`, `git status --short`, staged and unstaged diffs, untracked files, `git branch --show-current`, `git remote -v`, and `git worktree list --porcelain`. Record the original source branch and immutable HEAD as `<recorded-source-head>`. Stop for detached HEAD or an existing merge/rebase. If already on the target branch, commit and push only the intended changes; never delete the target branch.
2. Resolve `<primary>` to `main` unless the user explicitly names another target. Run `git fetch origin`; verify repository and remote identity. Use the existing local target, or create it tracking `origin/<primary>` if only the remote target exists. If neither exists, report the missing target rather than choosing another branch. If the target is checked out in another worktree, stop and report its path; do not force-switch or remove a worktree.
3. Inventory intended uncommitted changes separately from unrelated work, including staged, unstaged, and untracked content. Committing the intended changes on the target is part of this workflow; do not invoke `commit-push-lore` automatically or create a preparatory source-branch commit. If scope is ambiguous, clarify before staging. When intended dirty changes exist, announce and create a path-scoped stash with `git stash push --include-untracked -m <unique-label> -- <intended-paths>`, record its immutable object ID as `<saved-work>`, and inspect its tracked and untracked contents against the inventory. Keep this recovery snapshot until completion and report it; use `apply`, never `pop`. If intended and unrelated edits share a file, or unrelated changes would obstruct switching or merging, stop without stashing or discarding unrelated work.
4. Switch to the local target with `git switch <primary>`, then update it using `git merge --ff-only origin/<primary>` when that remote ref exists. A divergent target requires reconciliation before continuing; never reset it. Record the resulting primary HEAD and the source HEAD as both pre-merge tips. Review local target commits that will also be pushed; clarify if their inclusion is outside the requested scope.
5. Before merging, inventory behavior, contracts, and tests unique to both pre-merge tips with the merge base, commit log, and two-sided diffs. Include the saved uncommitted changes in the inventory. Branch recency, the current checkout, and an easier-to-compile side are not authority.
6. Merge the recorded commit, not the mutable branch name, with `git merge --no-ff --no-commit <recorded-source-head>`, unless the repository or user explicitly requires another merge policy. Resolve merge conflicts under the contract below before restoring saved work. If the source is already included, continue to restore intended uncommitted work and perform push/cleanup; do not create an empty commit.
7. Apply `<saved-work>` on the target with `git stash apply <saved-work>` when a snapshot exists. Do not use `--index` over the merge index. Resolve any application conflicts under the same contract, verify restored tracked and untracked content against the inventory, and stage only intended paths or hunks. The recovery snapshot must remain available on failure. Do not absorb unrelated dirty files. Report conflicts that require product or ownership judgment.
8. Compare the resolved candidate with both recorded tips and the saved work, and verify every inventoried behavior and test is preserved or intentionally superseded. Run verification appropriate to the merged result. Passing tests alone are not sufficient because a conflict resolution can remove an implementation and its new or changed tests together. Review `git diff --cached --stat`, `git diff --cached --check`, and `git status --short` before committing.
9. Only after integration on the target, create the merge commit (or a normal commit when only uncommitted work is new) using the repository's message policy. When no Lore policy exists, use an intent-first message with actual `Tested:` evidence and any known `Not-tested:` gaps. If a merge is pending, finish its commit even when its tree matches the target; otherwise skip empty commits. Immediately prove inclusion with `git merge-base --is-ancestor <recorded-source-head> HEAD`; do not push if it fails. Record the final target HEAD as `<integrated-head>` so verification also covers the newly committed work.
10. Push only the target with `git push origin <primary>`, then fetch it again and prove both `<recorded-source-head>` and `<integrated-head>` are ancestors of `origin/<primary>`. If push or verification fails, retain the source branch and recovery snapshot and report the failure; never force-push. Do not push or delete the remote source branch.
11. Confirm the current checkout is `<primary>`. Before deleting, verify the original local source branch still points to `<recorded-source-head>`, is distinct from the target, is not checked out in any worktree, and is included in both the local and remote target. Then run `git branch -d -- <source>` as the final mutation. This workflow includes local source-branch deletion; no additional confirmation is needed for that requested cleanup. If any check fails or safe deletion is refused, retain the branch and report incomplete cleanup; never use `-D`.
12. Confirm the push range, `git rev-parse --short HEAD`, `git status --branch --short`, target/remote divergence, and absence of the original local branch. Report source branch and recorded HEAD, target branch, integrated commit, remote ancestry proofs, verification, deletion result, remaining local changes, and any retained recovery snapshot. Success requires remaining on the target with the source branch deleted (except when source and target were the same).

## Conflict-Preservation Contract

- Do not resolve a whole conflicted file with `ours` or `theirs`, or treat one parent as authoritative. Resolve from the common ancestor hunk by hunk so additions from both parents remain visible.
- Maintain a Conflict ledger in the merge commit body and final report. For every conflicting behavior, contract, test, and documentation change, record `preserve`, `integrate`, or `intentional removal`, plus the supporting verification. Prefer integration when both parents contain valid additions.
- Never delete or weaken new or changed tests merely to make the merged suite pass. Restore the intended behavior or escalate the genuine contract conflict.
- Intentional removal of code, behavior, or tests requires an explicit user instruction or approved repository requirement that names the removed capability. Record that authority in the Conflict ledger. A clean build, green tests, branch age, verbal urgency, or merge convenience is not deletion authority.
- Preserve all uncommitted and unrelated code. Do not use reset, checkout-overwrite, stash-and-drop, or cleanup commands as conflict-resolution shortcuts.

## Boundaries

- Never force-push, rewrite shared history, or silently choose a different remote or primary branch.
- Never commit intended source changes before integrating them on the local target. Do not represent fallback/legacy verification as acceptance evidence.
- Do not claim a merge complete until the two-tip semantic audit is complete; textual conflict resolution and a green suite are only intermediate evidence.
- If repository identity or the intended remote is ambiguous, stop before pushing and report the exact mismatch.
