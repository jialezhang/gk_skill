# Goal 复盘

## 目标

从原始证据重建 Goal 的真实执行结果、成本、偏差与可复用决策。把“已实现”“已启用”“已执行”“已验证”“已完成”分开判断，不用叙事替代证据。

## 工作流

### 1. 锁定复盘对象

先记录并核对：

- Goal objective、Goal ID、thread/task ID、创建与结束时间、最终状态；
- 请求的产品/模块/版本、UI 入口、API 路由、feature flags、runtime/provider；
- 分支、commit/build/release、工作树状态、测试数据根目录与端口；
- 原始范围、范围变更、明确非目标。

若用户指定的 Goal 仍含糊，先搜索已有 Goal 记录、目标数据库和相关交付文档，以 objective、日期、thread 或 commit 匹配；不得随意选择最相近的 Goal。若仍有多个候选，列出歧义并请求用户指定。

当前 Goal 可读取时调用 Goal 状态工具；历史 Goal 优先读取已有 `docs/goal记录/`、Goal 数据库或完成回执。只读复盘不得更新、关闭或重启 Goal。

### 2. 建立证据清单

按以下优先级取证：

1. Goal 系统状态与完成回执：objective、status、`tokensUsed`、`timeUsedSeconds`、时间戳。
2. 精确目标的原始验收证据：测试输出、浏览器/API/受保护资源证据、外部副作用记录、release/build identity。
3. 批准的 PRD、实施计划、任务清单、delivery state 与最终验收文档。
4. Git commit、diff、分支、工作树与运行环境身份。
5. rollout/token ledger、trace、session 或子 agent 记录。
6. 聊天叙述和人工回忆；只能作为待核对线索。

为每个核心结论保留来源路径、命令输出或不可变 ID。找不到证据时写“未采样”“无法从当前系统恢复”或“未验证”，不得反推或补造。

### 3. 区分统计口径

至少区分：

- 墙钟时间：自然时间窗口，可包含等待或并行；
- Goal 有效执行时间：Goal 系统计；
- Goal 聚合 Token：Goal API 口径；
- rollout/model Token：可能包含缓存输入、递归上下文和子 agent；
- 有效新增 Token：仅在原始账本支持时计算；
- 阶段/模型/会话分项：仅在有采样或 ledger 时填写。

不同口径不得相加、互相替代或按比例猜测。并行阶段的时间不得直接相加后声称为实际工期。模型路由以实际运行 metadata 为准，不以 agent 名称、计划角色或插件名称推断。

### 4. 重建执行与证据有效性

按真实阶段重建执行链，而不是照抄原计划。每个阶段记录目标、动作、结果、证据和统计可用性。

单独建立“作废/诊断运行”表，至少说明：

- 运行身份与现象；
- 失效原因：错误目标、源码已变、端口占用、fixture/harness 缺陷、共享状态污染、证据缺失等；
- 该运行能证明什么、不能证明什么；
- 纠正动作与最终有效证据。

错误目标或失效运行不得作为验收证据。代码、配置、fixture 或目标身份在验收后改变时，旧结果自动失效，除非能证明变更不影响该结论。

### 5. 对账交付状态

逐项核对计划任务、验收 Gate 和核心用户旅程，并使用以下状态：

- `IMPLEMENTED`：行为存在于代码；
- `ENABLED`：当前运行时可达；
- `EXECUTED`：精确目标路径实际运行；
- `VERIFIED`：取得可复核验收证据；
- `BLOCKED`：有明确阻塞；
- `DEFERRED`：用户或计划明确延期；
- `INVALID`：证据或运行作废。

只有核心范围全部达到 `VERIFIED`，且 Goal 系统状态与证据一致时，才写 `COMPLETE`。Goal 仍为 active/paused/blocked 时，生成“阶段复盘”并明确当前状态；不得为了文档完整把它写成完成。

### 6. 提炼因果与行动

分别提炼：

- 做得有效的做法：写成“行为 → 结果 → 证据”；
- 偏差与浪费：写成“现象 → 根因 → 后果 → 恢复动作”；
- 不能为了提速删除的门禁；
- 可压缩的等待、重复验证、上下文复制或文档成本；
- 下一轮约束：写成可执行规则、owner、触发条件和验收条件；
- 剩余风险与明确非目标。

避免泛化为“加强沟通”“提高效率”。每项建议必须能够在下一次 Goal 开始前、执行中或验收时被检查。

### 7. 生成复盘文档

写完整复盘时先读取 [references/report-template.md](references/report-template.md)，按证据情况裁剪可选章节，不要为凑模板编造内容。

若仓库已有 `docs/goal记录/`，默认创建或更新：

`docs/goal记录/YYYY-MM-DD-<goal-slug>-goal-retrospective.md`

遵守仓库的文档语言、文件命名和数据保护规则。优先更新已有同一 Goal 复盘，避免重复文档。用户只要求摘要时直接输出摘要，不擅自写文件。

## 写作约束

- 默认使用简体中文；代码标识、路径、Schema 和协议名保持原文。
- 先写结论与证据，再写过程。
- 明确标注事实、推断和建议；推断必须说明依据。
- 对关键数字注明来源和口径。
- 对全量测试、浏览器验收、外部副作用和发布状态分别陈述，不能互相替代。
- 不把诊断结果、legacy/fallback 路径、schema/stub 或局部 milestone 包装为完整交付。
- 引用精确文件路径、commit、run/job/release ID；不复制敏感 payload、凭据或受保护数据。
- 若复盘发现现有 Goal 状态与证据矛盾，报告不一致；除非用户另行要求，不修改 Goal 状态。

## 最终交付

完成后简要报告：

- 复盘对象与最终状态；
- 生成或更新的文档路径；
- 使用的权威证据；
- 未采样、未验证或仍有争议的部分；
- 最重要的 1～3 条下一轮行动。
